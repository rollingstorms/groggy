# Groggy current-state review

**Review date:** 2026-10-19  
**Checkout:** `develop-viz-redo` at `88ad28dc` (the same commit as `origin/develop-viz-redo` when fetched on the review date)  
**Purpose:** Reconcile the implementation with Groggy's accepted design before treating the Graphiti-oriented roadmap as a build plan.

## Executive summary

Groggy is a substantial graph analytics library, not an unbuilt graph engine. Its Rust core already has graph identity, active topology, directed/undirected configurations, parallel edge IDs, columnar attributes, subgraphs, graph/table/array/matrix conversions, query filters, traversals, eleven registered graph algorithms, an algorithm builder, history structures, temporal indexes, and visualization. The Python package and PyO3 bridge expose much of that work. A single node with no edges is a working minimal graph case. An empty `Graph` is also supported as the state before nodes are added.

The architectural decisions are documented and accepted: a Rust core with a thin FFI and Python interface, separate topology and signal, columnar data, connected views, attribute-first processing, and Git-like history. The review should preserve those decisions unless a demonstrated contradiction or new use case requires changing them. See [design decisions](../../docs/appendices/design-decisions.md), [origins](../../docs/concepts/origins.md), and the [concepts overview](../../docs/concepts/overview.md).

The largest **correctness gap** is the path from live property changes into historical commits: it records placeholder strings instead of actual values. There are also confirmed inconsistencies in live-edge reads and direction-aware traversal. The largest **product gap for Graphiti** is durable, recoverable storage and a compatible adapter/driver, not basic node-and-edge implementation. The earlier [implementation roadmap](../planning/graph-engine-implementation-roadmap.md) overstated how much is new; its items are reclassified below.

## Scope and method

This is a repository-wide architectural and capability review, not a line-by-line proof of every API. The tracked tree contains approximately 112,363 lines of Rust core in 196 files, 36,654 lines of Rust FFI in 62 files, 17,734 lines of Python package code in 57 files, 16,382 lines of Python tests in 42 files, and 185,463 lines of notes and documentation. I inspected the public facades, module boundaries, accepted ADRs, representative implementations and tests for each major subsystem, searched for explicit stubs, and ran the test suites and focused runtime probes. A passing test is evidence for its covered behavior, not a general correctness certificate.

## What the earlier 34-item roadmap gets wrong

The roadmap reads as if Stage 1 must invent a graph model. That is incorrect. It also puts broad Graphiti backend requirements in the same dependency chain as Groggy's own architectural repairs. The classification below is a better starting point. “Existing” means a substantive implementation exists, not that every behavior is correct.

| Roadmap items | Correct classification and next question |
| --- | --- |
| 1 | **Established design; verify.** Accepted ADRs and APIs already define the engine's shape. The canonical minimal graph case is one node, zero edges. Gather existing invariants and identify contradictions; do not redesign the contract. |
| 2-3 | **Repair.** Live-state and direction semantics disagree across existing paths. |
| 4 | **Existing kernel capability.** Distinct parallel edge IDs and self-loops already work; verify behavior across views, history, serialization, and any Graphiti mapping. Relationship type semantics are a separate extension. |
| 5 | **Repair.** Align bulk and single-operation validation/error behavior. |
| 6 | **Adapter/index extension.** Internal IDs exist. External UUID lookup and idempotent upsert can first live at the Graphiti boundary; promote only reusable pieces into the core. |
| 7 | **Existing rich type system, repair round trips.** Do not replace `AttrValue`; preserve its values through history, Python, and disk, and add temporal types only if the boundary needs them. |
| 8 | **Partly represented as attributes; design choice.** `entity_type` and flexible attributes already exist. First-class labels, ontology enforcement, and uniqueness constraints need a clear use case before becoming core primitives. |
| 9-10 | **New storage-grade guarantees over existing APIs.** `commit` and exports are not atomic ingest transactions or crash-recoverable history. Decide whether Groggy itself should become a durable embedded database or remain a computation engine with a storage adapter. |
| 11-13 | **Critical repair/completion.** Historical values, exact checkout, reset, and diff must match the Git-like vision. |
| 14-15 | **Partial foundations.** Branches, merge-commit representation, ancestry, and lower-level GC exist; conflict-aware merge and public GC semantics remain incomplete. |
| 16-17 | **Graphiti domain extension.** Fact-valid time and episode provenance differ from Groggy's commit history; model them in the adapter/domain layer before changing the history kernel. |
| 18 | **Index extension.** Active-state and attribute-index structures already exist, but database-style UUID/property/time indexes are not demonstrated. Build only those justified by measured queries. |
| 19 | **Existing broad API, verify parity.** Python exposure is not a new stage; close gaps as each repair ships. |
| 20 | **New integration.** A lossless Graphiti data adapter is a reasonable first proof. |
| 21 | **Existing filtering/traversal, extend selectively.** A general query language or Cypher parser is a separate product decision. |
| 22-24 | **New retrieval capability, possibly pluggable.** Full-text, vector indexing, and result fusion may live behind interfaces rather than inside the graph kernel. |
| 25 | **New optional integration.** A full Graphiti backend driver should follow an adapter proof and an explicit decision that Groggy should own durable storage and search. |
| 26-27 | **Existing distinctive features, repair semantics.** Views and table transformations are part of the core identity of Groggy, not future foundations. |
| 28-30 | **Existing analytics stack, correctness/completion work.** Algorithms, matrix infrastructure, and builder already exist; repair wrong results and decide which advanced branches remain in scope. |
| 31-34 | **Cross-cutting validation and operations.** Tests, benchmarks, and docs already exist, but should measure the repaired core and any chosen deployment model. |

## Recommended architecture boundary for the Graphiti idea

1. **Keep Groggy's core identity.** Preserve topology/signal separation, columnar attributes, graph/table/matrix transformations, and the three-tier Rust/FFI/Python structure. Do not add Graphiti nouns to the graph kernel merely because Graphiti is the first consumer.
2. **Repair semantic invariants before expansion.** Live membership, directedness, and historical property values affect existing users and every future integration.
3. **Prove a narrow data adapter.** Map Graphiti UUIDs, episodes, entities, facts, validity fields, provenance, and embeddings into existing Groggy nodes, edges, and attributes. Test lossless round trips and updates before deciding on first-class labels or time types.
4. **Decide what “store” means.** If Groggy is to replace Graphiti's graph database, it needs atomic writes, durable history, recovery, indexing, and a driver. If it is an embedded analytical companion, it can ingest exported Graphiti state while another system remains the durable store. Both are coherent; they are different products.
5. **Keep search modular.** Graphiti combines graph traversal, keyword search, and vector similarity. The latter two may be separate indexes/services attached to Groggy rather than permanent dependencies of its minimal graph model. A full Graphiti driver requires the integrated behavior whichever architecture is chosen.

## Review conclusion

Groggy has a large, distinctive implemented core. Its main issue is **semantic integrity at subsystem boundaries**: active topology versus pool, directed graph versus traversal, live attributes versus history and disk, and view claims versus materialized tables. Treat those as focused repairs to an existing engine. A Graphiti backend is an extension project whose storage and search responsibilities should be chosen explicitly after a narrow ingest proof. The previous PDF workbook should be considered provisional until its prompts are rewritten around this current-state map.
